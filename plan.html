Project 1: Production RAG with citations

Written together, one section at a time, before any code.

How the system works

The LLM does not search, and it does not choose anything. Our code does the search. The LLM only writes the answer from the chunks that our code gives it.

Three models, three jobs

ModelJobWhen it runs
Embedding model (bge-small, bge-m3)Turns text into a vectorIngestion: every chunk. Question time: the question.
Reranker (bge-reranker-v2-m3)Scores how well a chunk answers the questionQuestion time, on 50 chunks
LLM (Qwen3 8B)Writes the answer from the chunks it is given. At ingestion, writes a context line per chunk and table summaries.Ingestion: once per chunk, on a subset. Question time: one small call before search (company names), and one call to write the answer.

Diagram

Phase 1: ingestion, once, before any question

  1. Download 1,000 filings.
  2. Parse each one into Items, sections, pages, and tables. Tables become their own chunks, and the prose keeps a placeholder that points to each table.
  3. Cut the sections into chunks of about 400 tokens.
  4. Add the prefix to each chunk: Acme Corp | FY2025 | Item 1A | Supply chain risk.
  5. Contextual retrieval: ask the LLM to write one or two sentences that say what the chunk is about, in the context of its filing, and put them after the prefix. Table summaries (option 3) are the same kind of step. This is the only LLM work in phase 1. It is one call per chunk, so it runs on a subset. Nothing changes at question time: the chunks are only better described.
  6. Send each chunk to the embedding model. It returns a vector. This is where every embedding comes from. The LLM never makes one.
  7. Store each chunk in Postgres: text, vector, page, section, company.
  8. Build the BM25 word index from the same chunk texts. BM25 uses words only, and no vectors.

Phase 2: one question

The user asks: "What did Acme say about tariffs on Vietnam?"

  1. Company router. Our code asks the LLM one small question: which companies does this name? Answer: Acme. Search is filtered to Acme's filing. If the router names several companies, steps 3 to 6 run once per company, with a budget per company, and the results are merged before step 7. If it returns "general", the search runs across all filings with a cap per company.
  2. Embed the question. The embedding model turns the question into a vector.
  3. Vector search. Postgres finds the 50 chunk vectors closest to the question vector.
  4. BM25 search. The 50 chunks with the best word match for "tariffs" and "Vietnam".
  5. RRF merge. The two lists become one, by rank: 1 / (60 + rank) summed over both lists.
  6. Rerank. The reranker reads the question with each of the 50 chunks and scores them. Keep the top 8.
  7. Parents. Look up the section of each of the 8 chunks. This is small-to-big.
  8. Prompt. Our code builds one prompt: the instruction, the sections with their chunk IDs and pages, and the question.
  9. LLM. Qwen reads the prompt and writes the answer with citations. This is the first time the LLM sees the question in full.
  10. Check. Our code checks that each cited chunk exists and that the quote is in it. Then it shows the answer.

Where the "understanding" happens

  • Before the search, the embedding model reads the meaning of the question. It is a small model with no reasoning, but it does read meaning. That is why "tariffs on Vietnam" can match "trade duties on Southeast Asian imports".
  • The LLM reads the question in full only in the final prompt, together with the retrieved text.
  • The LLM makes no decisions about how to search in project 1. Query rewriting, judging the results, and searching again are project 2, the self-correcting RAG.

What we test

Each box in the diagram is a choice, and the plan tests the choices one at a time, with the same questions: how to chunk, which embedding model, which search method, which reranker, how to handle tables, how to describe chunks, and how the LLM answers with and without retrieval.

Limits of project 1, and what project 2 adds

Project 1 embeds the question as written and searches once (once per named company). The LLM makes no decision about how to search. Project 2 is a different architecture: the LLM reads the question first, plans the searches, checks the results, and tries again. These are the cases that project 1 cannot handle.

Project 1 cannot handleWhyProject 2 adds
Multi-part or paragraph-length questionsOne vector for several topics matches nothing wellQuery decomposition: split into simple questions, search each one

The golden set includes about 10 multi-part questions. Project 1 is expected to score low on them. That score is the baseline that project 2 must beat.

3Ingestion and parsing: standardization

The SEC files do not arrive in one format. The parser normalizes each filing into one standard structure. The standard is the SEC Form 10-K Item list. After this step, the rest of the system never sees HTML differences between companies.

filing
  company, ticker, fiscal_year, accession_no, source_url
  items
    item: "1A", title: "Risk Factors"
      sections
        title, page_start, page_end, text

Cases the parser must handle

  • Page numbers in different places (footer, header, number first or last). The output always has page_start and page_end.
  • Integrated annual reports with no Item headings, mostly large banks. Map sections to Items with the cross-reference index.
  • Combined Items, for example "Items 7. and 7A.". Decided: split the text into separate Items, so every filing has the same Item structure.
  • Items incorporated by reference (usually 10 to 14). Keep the sentence and flag the Item.
  • Items that smaller reporting companies can omit (for example 1A, 6, 7A). Record the Item as "not required". This is correct, not an error.

Tables

Tables are parsed apart from prose. HTML gives the grid directly: <table>, <tr>, <td>. For each table:

  1. Layout or data. A data table has at least 2 columns, at least 3 rows, and several numeric cells. A layout table (for example a one-column bullet list) is unwrapped into prose.
  2. Title and units. The nearest heading or bold line above the table, plus the unit line, for example "(in millions, except per share data)".
  3. Header rows. Multi-level headers with merged cells are flattened to one label per column.
  4. Body rows. The first cell is the row label. Split number cells ($, 1,204, )) are merged into one number. Parentheses mean negative. Indentation gives the row hierarchy.
  5. Two forms stored. Structured JSON (title, units, headers, rows) for the LLM and the viewer. A text form for embedding and BM25, for example Net revenue | 2025: 1,204 | 2024: 1,090.
  6. Placeholder in the prose. The table's place in the section text gets a line such as [Table: Consolidated Statements of Operations]. The table chunk stores its section and position, so both link to each other.
  7. Page from the page break that the table sits in.

Checks on every filing

  • Required Items are present. Items that the filer can omit do not count as missing.
  • Every number tagged with ix:nonFraction in the inline XBRL appears in a parsed table cell. This is exact ground truth from the filing itself.
  • The count of data tables is in a normal range.
  • Items follow SEC order, or are mapped through the cross-reference index.
  • Each Item has a normal size.
  • No text is lost or counted twice.

A filing that fails a check is not indexed. It goes on a failure list with the reason.

4Eval harness and metrics

Four parts: golden set, metrics, runner (one command), results log (every run saved).

Golden set

  • 100 to 150 questions, split into a development set (about 100) and a test set (about 50). The development set chooses the winners. The test set runs one time, at the end, on the final system only.
  • Written by a subagent that reads the filings. Every question must have one definitive answer in the filing.
  • Each case: question, filing, evidence text, Item, page, reference answer, question type.
  • A hit is a retrieved chunk that contains at least 80% of the evidence text. Not a chunk ID, because each of the 7 chunking strategies makes different chunks. The partial match covers evidence that a fixed-size cut splits in two.
  • Chunk sizes differ, so strategies are compared at the same number of retrieved tokens (for example 2,000), not only at the same k. A large chunk contains more evidence only because it is larger.
  • Question types: fact lookup, number from a table, paraphrased, exact term, general (across companies), unanswerable, and multi-part (about 10 questions, expected to fail in project 1, the baseline for project 2).
  • Every retrieval score is reported for prose questions and table questions apart. The chunking comparison (section 5) needs this split for its sanity check.

Metrics

MetricChecked by

Confidence intervals: every score is reported with a 95% bootstrap confidence interval, for example "72% ± 2". To compare two configurations: draw the same number of questions at random from the set, with repeats allowed, compute the difference, and repeat 1,000 times. The middle 95% of the differences is the interval. If the interval includes 0, the two configurations are not different.

LLM judge design

  1. Code first. Use the judge only for what code cannot check.
  2. One judgment per call. Separate prompts for correctness, faithfulness, citation support, and refusal.
  3. Labels, not scores. For example correct / partial / incorrect, each with a written definition. No 1 to 10 scales.
  4. Reason before label. The judge writes a short reason, then the label, as structured JSON.
  5. Faithfulness by claims. Split the answer into claims. Check each claim against the retrieved text. Score = supported claims / all claims.
  6. Different model from the answer model. A model tends to prefer its own writing. Decided: gpt-oss-20b (OpenAI family, 21B, local through Ollama, free) judges Qwen3 8B, for all four judgments. Fallback if calibration fails: Claude Haiku 4.5 for correctness and refusals only, which costs a few cents per run.
  7. Fixed settings. Temperature 0, a versioned prompt, and the judge version saved with every result.
  8. Calibration. A person labels a sample of answers. Measure agreement with the judge. Fix the prompt until agreement is high. Keep a separate held-out sample to confirm, so the prompt does not overfit.
  9. Consistency check. Run the judge 3 times on a subset. Labels that change between runs show an unclear rubric.

Human checks (agreed): you label about 40 answers to calibrate the judge, and you spot-check about 15 of the subagent's questions.

5Chunking (three strategies)

Only the section level is chunked. Items and documents are too large to embed well: bge-small reads 512 tokens and bge-m3 reads 8,192, and one vector for a long text averages many topics.

LevelRole
Chunk (inside one section)The unit that we embed and search.
SectionThe parent. Small-to-big sends it to the LLM for context.
ItemA filter and a citation field.
DocumentA filter (company, year) and a citation field.

Strategies to compare. Strategies 1 to 3 produce chunks of about 400 tokens. Strategy 4 needs a long-input embedding model.

  1. Fixed size, no structure (baseline). Cut every 400 tokens. Ignore sections and Items.
  2. Fixed size inside sections. Cut every 400 tokens, never across a section boundary.
  3. Paragraph-based inside sections. Join whole paragraphs up to about 400 tokens. Never cut inside a paragraph or across a section.
  4. Whole section as one chunk. One chunk per section, up to 8,192 tokens. bge-m3 only.
Strategybge-smallbge-m3
1. Fixed size, no structureYesYes
2. Fixed size inside sectionsYesYes
3. Paragraph-based inside sectionsYesYes
4. Whole section as one chunkNot possibleYes

7 indexes in total.

Token ruler: chunk sizes are measured with the bge-small tokenizer, which has the tighter limit (512). A chunk that fits bge-small also fits bge-m3. Both models embed the same chunk texts, and each model splits the text with its own tokenizer when it reads it. Only the model changes between the two rows.
Trade-off to note: the chunk sizes are set for bge-small, not optimized for bge-m3. Strategy 4 is the only test of long inputs for bge-m3.

Tables are a separate axis. Tables are pulled out of the prose before chunking (section 3), so the chunking strategies cut prose only. If tables stayed in the prose, each strategy would cut them in a different way, and the chunking scores would mix two effects. The parent section keeps the table in its original place, so the LLM still sees prose and table together.

How search sees tables: the prose chunk holds a placeholder that points to the table. The table chunk is a separate, searchable chunk. The parent section holds both in the original order, and it is what the LLM reads. Search runs on both kinds of chunk.

Step 1, chunking comparison (the 7 indexes): prose chunks by strategy. Table chunks use one fixed default: embed the title, units, row labels, and column labels (option 2 below). Scores are reported for prose questions and table questions apart. Table-question scores must be about equal across strategies. If they differ, the axes interact, and the affected cells are tested in full.

Step 2, table comparison, on the winning strategy and model, measured on the table questions:

  1. Pointer only (baseline). The table is not indexed. It reaches the LLM only through the parent of a prose chunk that points to it. This tests whether direct search of tables helps at all.
  2. Back in the flow. The table text rows are merged back into the prose chunks of the winning strategy.
  3. Own chunk, labels only. Embed the title, units, row labels, and column labels. Send the full table to the LLM.
  4. Own chunk, summary. Embed a short LLM-written summary of the table. Send the full table to the LLM. Slow: about 100 summaries per filing with Qwen on the Mac. Run it on a subset: the filings that the table questions point to, plus a random sample of the same size. Options 1 and 2 are measured on the same subset for a fair comparison.

In all options, a table larger than the chunk limit is split by rows, and each part repeats the title and header row. Prose chunks and their vectors are reused between the two steps, because only the table chunks change.

Context prefix: before embedding, add Company | FY | Item | section title to the front of each chunk. Without it, a chunk does not say which company or section it is from. The stored chunk text stays clean, so citations quote only the filing text. This metadata prefix is the default in steps 1 and 2.

Step 3, contextual retrieval, on the winning strategy, model, and table option. At ingestion, the LLM writes one or two sentences per chunk that say what the chunk is about in the context of its filing. The sentences go after the metadata prefix, and the chunk with its context goes into both the vector index and the BM25 index. Nothing changes at question time. 6Embeddings

An embedding model turns text into a vector. Texts with similar meaning get vectors that are close together. Search embeds the question and finds the closest chunk vectors. It finds matches in meaning that share no words, which BM25 cannot do.

8Search: BM25, vector, hybrid

Three search methods, tested on the same eval questions:

MethodKindMatchesIndex
BM25Lexical (sparse)Exact wordsInverted index
VectorSemantic (dense)MeaningHNSW
HybridBothBothBoth, then merge

BM25 score rules: term frequency (more occurrences add more, with a smaller gain each time), rarity or IDF (rare words count more), and length (long chunks get a small penalty).

Hybrid merge: Reciprocal Rank Fusion (RRF) over the top 50 of each method.

score(chunk) = 1 / (60 + rank in BM25 list) + 1 / (60 + rank in vector list)

Question that the comparison answers: what does each method add, and does hybrid beat both?

Company routing: before search, the LLM reads the question and returns structured output: the companies that it names, or "general". Its instructions cover names in different forms (Apple, Apple Inc., AAPL), a company that is not in the corpus (returned with a flag, so the answer can say so), a vague reference ("the iPhone maker"), and no company at all. The eval measures how often the router is right, because a wrong route gives a wrong answer whatever the search does.

One search per company: for each named company, our code runs the same search with the filter set to that company, and keeps a budget per company (for example the top 4 chunks after reranking). The results are merged, and the parent sections of all companies go to the LLM in one prompt. This is a fixed loop in our code. The LLM does not decide to search more than once. That decision belongs to project 2.

General questions: the search runs across all filings, with a cap per company (for example 2 chunks), so one filing cannot fill the list. Limit to state in every such answer: search returns the best 50 chunks, not every match. A question such as "which companies mention X" is answered "among the filings retrieved", not in full.

BM25: in our own Python code, over the chunk text from Postgres. About 30 lines, and every rule is visible.

9Reranking

Search finds candidates fast. A reranker reorders them with a slower, more accurate model. Pipeline: hybrid search, top 50, then reranker, top 8, then parent sections to the LLM.

Bi-encoder (embedding model): embeds question and chunk apart, compares vectors, precomputed, fast. Cross-encoder (reranker): reads question and chunk text together, returns one score, runs per question, slow. Both compare meaning, not only words.

10Answer generation, grounding, and citations

The answer reaches the user in three layers.

  1. Answer with citation markers. Each claim has a number, for example [1], that points to a source.
  2. Citation card. Company, fiscal year, Item, section title, page, and the exact quote that supports the claim. The quote lets the user check the claim, and lets the system test grounding: if the quote is not in the stored chunk, the citation is wrong.
  3. Our own viewer. A click on a citation opens our page. The page shows the stored section with the quote highlighted, and the page number next to it. A link to the original filing on sec.gov is also on the page.

Answer format: each citation gives the chunk ID and the exact quote. Code checks that the quote is in that chunk.

Answer not in the text: the model says that the filings do not contain the answer, and gives no citation. It never answers from its own knowledge.

Viewer: the frontend is not a concern now.

11Prompting baseline and model choice

  • Small-to-big: search on small chunks, then send the parent section to the LLM.
  • Context budget: at most 20,000 tokens of retrieved text per question. Qwen3 8B has 40,960 tokens, and the prompt, thinking, and answer need the rest.
  • Baselines and main runs:
    RunModelContextShows
    AQwen3 8BNo documentsWhat the small model knows alone
    BQwen3 8BOur RAG systemThe system that we build
    Run A is the prompting baseline to beat. Haiku runs (no documents, and the full 10-K) are shelved: the full-10-K run costs about $16 per run. A full 10-K does not fit in Qwen3 8B (40,960 tokens), so Qwen gets no full-10-K run.
  • Thinking mode: every Qwen3 run (A and B) runs twice, with thinking on and with thinking off.
  • Run time: Qwen3 8B writes about 20 to 30 tokens per second on the Mac. With thinking on, one answer can take about a minute, so one run of 100 questions can take 1 to 2 hours. Embedding with bge-m3 is also slow. Time a small sample before each full run.
  • Memorization: models are trained on public web data, which includes SEC filings. Control this with filings published after the model's training cutoff, and with a no-retrieval run that shows what the model already knows.
  • Answer model: Qwen3 8B, local through Ollama (qwen3:8b, already installed). Free to run.
  • Training cutoff: Qwen3 was released in April 2025, so its training data ends before that date. Filings filed from July 2025 are after the cutoff.
  • Judge model: gpt-oss-20b, local and free. A larger model from a different family judges the smaller model. Haiku 4.5 is the fallback (section 4).
  • API key (for the Haiku fallback): ANTHROPIC_API_KEY is in .env in the project root. .gitignore lists .env, so Git never commits the key. File mode 600.

14Glossary

Terms that we learn along the way.

Chunk
A piece of a document that is embedded and searched as one unit.
Embedding
A vector (list of numbers) that represents the meaning of a text.
Small-to-big
Search on small chunks, then send the larger parent section to the LLM.
Lexical search (sparse)
Search that matches words. BM25 and TF-IDF are examples. Each text is a long, mostly-zero list with one position per vocabulary word.
Semantic search (dense)
Search that matches meaning with embedding vectors. The vectors are short and every position has a value.
BM25
A lexical ranking function. It scores by term frequency, word rarity (IDF), and chunk length.
IDF
Inverse document frequency. A word that occurs in fewer chunks gets more weight.
Hybrid search
Run lexical and semantic search, then merge the two result lists.
RRF
Reciprocal Rank Fusion. Merges ranked lists by rank only: sum of 1 / (60 + rank).
HNSW
An approximate index for vector search. It links each vector to its near neighbors and walks the graph toward the question.
Inverted index
The index for lexical search. For each word, a list of the chunks that contain it.
Contextual retrieval
At ingestion, an LLM writes a short description of each chunk in the context of its document. The description is put in front of the chunk before it is embedded and indexed for BM25. Nothing changes at question time.
ANN recall
The share of the exact nearest neighbors that an approximate index finds.

How the build runs

The orchestrator (this session, Fable) never writes the implementation. For each task it writes a contract: inputs, outputs, file names, and the checks that prove the task works. A subagent implements the contract. The orchestrator runs the checks itself, and it does not trust the subagent's report. Every wave ends at a gate: the checks pass, the orchestrator reports in plain terms, and you approve before the next wave starts.
